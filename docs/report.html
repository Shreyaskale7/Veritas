1. Problem and approach

Marks and certificates are changed after the fact, quietly. Veritas makes that detectable and mostly impossible inside the database: the rules live in triggers, constraints and row-level security, so no application bug, direct SQL session or clever client can skip them. Every mark write is an append-only, hash-chained revision; revisions are sealed into Merkle batches whose roots are pinned in an external witness; certificates store only a salted hash and verify publicly with a QR code.

6. Tamper detection and threat model

Leaf = SHA-256('L' + row_hash); node = SHA-256('N' + left + right); the SQL merkle_root() and the Python merkle.py are cross-checked for equality. Row hashes use a canonical JSON array so free text cannot create ambiguity.

7. Concurrency and performance

A single global chain would serialise every writer. Veritas chains per course, so writers on different courses never wait for each other (concurrency tests C1-C3 prove same-course writers queue and other-course writers do not).

At 16 clients a per-course chain sustains 2057 tps against 301 tps for one global chain, 6.8x more.

An index on (course_id, seq) turns the "latest revision of a course" lookup from a 6.4 ms sequential scan into a 0.06 ms index scan.

10. Limits and future work

  • The witness is only outside the administrator's reach if it is pushed to a remote they do not control; on one machine it is tamper-evident, not tamper-proof. The immudb backend is written but untested.
  • Revisions made after the last anchor are not yet pinned; the scheduler shortens that window (default 15 minutes).
  • Single sign-on (OIDC) is not implemented; accounts use bcrypt passwords with throttling.
  • The Docker stack has not been run in the development environment (no Docker daemon).
  • The witness (one file or git repo) is shared by all institutions; records carry the institution slug and each admin only verifies their own, but the file itself is common.
